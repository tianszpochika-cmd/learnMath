## 1. 范围与定位

管理端是内容生产、审核、发布和运营观测的工作台。本稿按用户要求，将已形成的官网和 Web 学习端视觉语言延伸到管理端，同时保留管理任务需要的紧凑表格、持续可见的状态、明确的错误定位与可撤销操作。评审范围为 A01–A19 全 19 屏，重点审查 A04 图谱边、A11 路径编排、A12 推理链编辑三个复杂工作台。

原有 [19 屏原型](./index.html)仍可用于对照 17 号文档的旧版页面广度。新版 HTML 是本地交互评审材料；它与 `apps/admin` 的 Vue 页面、路由、接口、数据库、权限服务和发布能力彼此独立。页面中的演示记录、数字和变更状态只表达界面设计，不能作为真实用户数据、生产内容量、写操作审计或业务验收证据。

## 2. 品牌延展与管理任务的排版规则

| 元素 | 新版管理端用法 | 操作场景约束 |
|---|---|---|
| 品牌 | 数源标识、`#2F6BFF` 主蓝与克制的蓝紫焦点，延续官网和新版 Web 的视觉归属 | 渐变主要用于品牌区或主操作；危险、审核、待发布、校验失败使用明确语义色与文字，不用渐变代替状态 |
| 字体 | 页面级标题可用官网衬线字体，帮助建立模块层级 | 菜单、表格、筛选、表单、代码/DSL、题面与日志使用清晰无衬线字体；表格维持紧凑密度和稳定数字宽度 |
| 网格 | 细坐标网格可出现在登录品牌区、仪表盘欢迎区和编排画布 | 内容表、公式编辑、密集校验结果使用平静底色；画布网格必须服务定位与吸附，不遮盖连线或文字 |
| 主题 | 亮暗两套界面状态沿用官网和新版 Web 的方向 | 文本、分隔线、表格选中、校验错误和焦点在两主题都要可读；状态同时使用图标或文字，不只靠颜色 |
| 密度 | 沿用 AD1 的紧凑管理骨架和 AD2 的查询栏—表格—分页—操作列模板 | 不因品牌化扩大每行占高，也不将主操作藏在装饰性卡片中；复杂编辑优先保留上下文 |

17 号文档的 AD1/AD2 和 14 号官网文档的品牌规范原先分别面向管理端与官网；16 号文档 WD2 还明确限定 Web 学习端的旧视觉边界。本轮新增的是**供评审的跨端视觉方向**，不默默改写已评审的规范或既有实现。正式采用时，应把确认后的字体、主题、坐标纹理、组件 token 和适用范围同步回写相关设计文档与实现规范。

## 4. 核心旅程与交互审查

**内容入库到学员可见**：A03 创建知识点并在 A04 建立依赖边；A05/A06 编课程与课时；A07/A08 审核题目；A09/A10 组卷或测评；A11 编排路径。每一步保留草稿、校验与发布状态。发布后的学员可见内容来自已审核快照；缺题或缺卡应呈现“筹备/待补全”，不能让管理者误判为已可用。

**图谱加边 A04**：选起点、选终点后先在界面显示校验结果。发现环时用文字给出完整环路并标出冲突边；不能把红色节点单独当作诊断。原型可以演示前端镜像校验，但真实写入、跨引用体检和发布门禁仍以服务端结果为准。

**路径编排 A11**：左侧选素材，中间安排顺序，右侧编辑引用、解锁规则和 P6 坐标。保存与“可发布”应为不同状态；DSL schema 错误、前置不可达、晋级自锁循环、题池不足都要定位到资源或字段。缺真实题池时提供补齐任务或保留筹备态，不显示虚构的覆盖通过。

**推理链 A12**：每步的内容、依据挂点、动机和岔路分区清楚；拖拽改顺序不改变稳定步骤 ID。质量来源 `ai_draft`、工作稿审核状态、当前在线版本分别显示。提交校对不覆盖旧在线快照；审核发布有版本冲突说明，撤下单独确认。

**列表与抽屉**：A03/A05/A07/A15 等页沿用 AD2；回车搜索、筛选项可单独撤销、分页和行操作位置稳定。详情与轻量编辑优先用右侧抽屉；未保存时关闭需确认，复杂编辑进入独立页。删除、驳回、禁用、协议发布等危险写操作应有二次确认、结果与操作日志依据。本地演示的提示不得假称已写入真实审计日志。

**键盘、响应式与无障碍**：列表、菜单、抽屉、确认框与错误项应可用键盘操作，焦点可见、表单标签关联，快捷键不得劫持正在输入的字段。管理端桌面宽度 ≥1280 是主形态；1024–1279 可收起素材或属性栏；复杂画布在 <1024 时应提示桌面操作并保留只读信息，不伪装成可完整编辑。应分别审查亮暗主题、减少动态效果和文字/图标双重状态提示。

## 5. 业务与权限边界

- **课时完成 BR-02**：默认 `practice_required`，没有审核客观题则拒绝发布；纯阅读需显式选择并确认 `read_only`。学习者读完、完成课时和获得掌握度是不同状态，管理表单不能把它们合并。
- **作答策略 BR-03**：用途、`feedback_mode`、`assistance_policy` 分开配置并由服务端在开卷时冻结。测评、晋级战、Boss 和挑战赛一期只允许审核客观题，拒绝已公开同族题及不允许的辅助。普通考试可混合题型，但客观与自评成绩分开。
- **内容发布 BR-06**：工作稿 `status` 与内容齐全程度 `completeness` 独立；四卡、公式、推理链均有已发布快照。部分审核内容可以形成部分快照并标明缺失；待审修改不覆盖在线版本。发布用 `expectedRevision` 原子校验；撤下须明确操作。管理预览与公开接口分离并验证管理域权限。
- **覆盖门禁 BR-11**：覆盖矩阵必须根据真实内容清单产生，至少能定位节点 × 难度 × 题型、审核题族数、晋级题池、前置和路径引用。P4 可用格及独立晋级池遵守数量要求；没有内容时显示“内容筹备中”。示例 ID、演示数字或总题量不能证明覆盖充分。
- **权限与审计**：管理端登录、角色、写权限、Key 管理、操作日志均依赖真实服务端。演示中的登录、审计提示、连通灯、发布成功、报表导出只用于检验界面表达；没有后台响应时不可声称实际鉴权、投产或审计成功。

## 6. 验证与交付边界

评审时建议按 A01–A19 逐屏记录：信息层级、官网/Web 品牌一致性、主任务路径、错误恢复、禁发布原因、空/加载/失败状态、亮暗主题、桌面与收栏宽度。三个工作台重点检查输入→校验→更正→保存/发布的状态是否可辨，及危险操作是否有准确的结果反馈。

本地稿件可做结构、脚本和设计契约的静态检查。浏览器里的实际视觉、键盘、焦点、响应式和交互复核仍待在允许的环境中完成。静态检查、原型演示、`apps/admin` 的开发状态以及运行时验收须分别报告；不能据原型声称 19 屏已真实上线、内容发布已生效或管理端业务链已验收。
